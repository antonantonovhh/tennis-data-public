# tennis_parser

Сбор статистики по паре игроков из двух источников и склейка в один отчёт.

| Что | Откуда | Как забирается |
|---|---|---|
| H2H, карточки игроков, текстовое превью | tennisratio.com | статический HTML |
| История матчей + стата по подаче/приёму | tennisratio.com | **JS-рендер** (Playwright) |
| Elo, hElo/cElo/gElo, peak, ATP rank | tennisabstract.com | статический HTML |
| yElo (рейтинг по текущему сезону) | tennisabstract.com | статический HTML |
| Усталость и форма | считается локально | из истории матчей |

## Установка

```bash
pip install -r requirements.txt
playwright install chromium   # только если нужна история матчей
```

## Использование

```bash
# полный отчёт с таблицей в консоли
python -m tennis_parser.cli h2h "Jan Kumstat" "Maxim Mrva" --surface clay --summary

# сохранить JSON + два CSV с матчами
python -m tennis_parser.cli h2h "Jan Kumstat" "Maxim Mrva" --out out/ --summary

# только рейтинги
python -m tennis_parser.cli elo "Jan Kumstat" "Maxim Mrva"

# вся таблица Elo+yElo в CSV
python -m tennis_parser.cli dump-elo --csv elo.csv
```

Как библиотека:

```python
from datetime import date
from tennis_parser import Fetcher, fetch_h2h, load_ratings, compute_fatigue
from tennis_parser import blended_elo, elo_win_probability

f = Fetcher()
h2h = fetch_h2h(f, "Jan Kumstat", "Maxim Mrva")
ratings = load_ratings(f, "atp")

a, b = ratings.get("Jan Kumstat"), ratings.get("Maxim Mrva")
p = elo_win_probability(blended_elo(a, "clay"), blended_elo(b, "clay"))

fat = compute_fatigue(h2h.matches_p1, date.today())
print(p, fat.fatigue_score, fat.fatigue_label)
```

## Ключевые флаги

| Флаг | Смысл |
|---|---|
| `--mode auto\|static\|render` | `auto` пробует статику → встроенный JSON → Playwright |
| `--headed` | показать окно браузера (отладка селекторов) |
| `--surface hard\|clay\|grass` | какое покрытие брать для прогноза |
| `--surface-weight 0..1` | доля покрытия в смеси с общим Elo (по умолчанию 0.5) |
| `--best-of 3\|5` | поправка на формат в Elo-вероятности |
| `--as-of YYYY-MM-DD` | считать усталость на прошлую дату (для бэктеста) |
| `--simulate` | посчитать Монте-Карло симуляцию после отчёта |
| `--runs N` | прогонов симуляции (по умолчанию 10000) |
| `--elo-weight 0..1` | вес Elo в рабочей модели (по умолчанию 0.7) |
| `--force` | обойти кэш |
| `--cache ''` | выключить кэш совсем |

## Модель усталости

Минуты на корте не публикуются, поэтому оцениваются из счёта:
`геймы × 4.2 мин` + 12 мин штрафа за решающий сет. Дальше:

- `load_index` — сумма минут за 28 дней с экспоненциальным затуханием (период полураспада 7 дней);
- поверх накидываются штрафы за матчи в идущие подряд дни, за трёхсетовики, за ≥4 матчей в неделю, за смену покрытия;
- отдых гасит: 7+ дней — ×0.5, 14+ дней — ×0.25;
- итог `fatigue_score` 0–100 с ярлыком (свежий / нормально / накопленная нагрузка / устал / перегружен).

Константы вверху `fatigue.py` — под калибровку на своих данных. Как есть это разумная эвристика, а не проверенная модель; прежде чем ставить на неё деньги, прогоните бэктест на исторических матчах через `--as-of`.

## Симуляция матча

`simulation.py` считает Монте-Карло поверх уже собранного отчёта: новых
запросов в сеть не делает, 10 000 прогонов занимают около полусекунды.

Гейм считается замкнутой формулой, тайбрейк — динамическим программированием,
случайность остаётся только на уровне геймов и сетов. Поточечная симуляция дала
бы то же распределение в сто раз медленнее, а на кнопке в телеграме это заметно.

Считаются четыре модели, потому что стата и Elo регулярно расходятся:

| Модель | Из чего |
|---|---|
| `stats` | только подача/приём за 52 недели, с поправкой на приём соперника (Klaassen–Magnus) |
| `elo` | SPW подогнан бинарным поиском так, чтобы вероятность матча совпала с Elo-прогнозом |
| `blend` | 50/50 между ними + штраф за усталость |
| `work` | рабочая: `TP_SIM_ELO_WEIGHT` (0.7) на Elo + штраф за усталость |

Расхождение больше 20 процентных пунктов помечается предупреждением в чате.
Обычно оно означает, что проценты набраны против разной по силе сетки: игрок
с отличным приёмом на уровне ITF и игрок с посредственным приёмом на челленджерах
дадут одинаковые цифры при разнице в Elo под 400 пунктов.

Штраф за усталость растёт по ходу матча (1.0 / 1.8 / 3.0 п.п. SPW по сетам при
разнице `fatigue_score` в 60 пунктов), 35% штрафа возвращается свежему игроку
бонусом на его подаче. Множитель ограничен сверху, чтобы разница в 100 пунктов
не выкручивала первый сет. Константы — вверху `simulation.py`.

В чат уходят: вероятности по всем моделям, точный счёт по сетам с кэфами, тотал
геймов вокруг медианы, форы, вероятность решающего сета и разбор «как посчитано».

Если данных нет совсем — ни сравнения, ни Elo — блок просто не отправляется.
Если есть только одно из двух, считается то, что есть, с пометкой.

Это модель, а не прогноз. Штрафы за усталость — эвристика, проценты — из
52-недельной выборки без учёта уровня соперников. Прежде чем ставить деньги,
прогоните бэктест через `--as-of`.

## Что может сломаться

1. **История матчей на TennisRatio.** В статическом HTML таблицы пустые (`0 matches`) — данные подтягивает DataTables. Парсер сам переключается на Playwright. Если сайт сменит вёрстку, правьте `_render()` и `_find_match_tables()`. Часто быстрее найти XHR-эндпоинт в DevTools → Network и дёргать его напрямую через `Fetcher.get_json()` — тогда браузер не нужен вообще.
2. **Сопоставление имён.** TennisAbstract пишет имена без диакритики (`Jan Kumstat`), а другие источники — с ней. `names.match_name()` работает в три захода: точное совпадение → перестановка частей → уникальная фамилия. Однофамильцев (`Blanch`, `Svajda`, `Cerundolo`) проверяйте вручную.
3. **Retirement/walkover.** При `RET`/`W/O` победитель по счёту не определяется — `Match.won = None`, и такой матч не попадает в серию побед. В нагрузку геймы засчитываются как есть.
4. **Покрытие матча.** Определяется по названию турнира (`M25 Bad Waltersdorf, Clay`). Если покрытия в названии нет — `surface = None`.
5. **Rate limiting.** По умолчанию 1–2.5 с между запросами + кэш на 6 часов. Elo обновляется раз в неделю (`Last update` парсится в поле `updated`) — не гоняйте с `--force` без нужды.

## Телеграм-бот на Ubuntu-сервере

### Установка одной командой

```bash
git clone <ваш-репозиторий> tennis-bot && cd tennis-bot
sudo bash deploy/install.sh
sudo nano /opt/tennis-bot/.env      # вписать TELEGRAM_BOT_TOKEN
sudo systemctl start tennis-bot
sudo journalctl -u tennis-bot -f
```

Скрипт делает: системные пакеты → системный пользователь `tennisbot` → venv в
`/opt/tennis-bot/.venv` → `playwright install --with-deps chromium` (на голом
сервере без этого хромиум не стартует — не хватает системных библиотек) →
unit-файл systemd с автозапуском.

### Команды бота

| Команда | Что делает |
|---|---|
| `/h2h Игрок 1 \| Игрок 2 [clay\|hard\|grass] [bo5]` | полный отчёт таблицей |
| `/elo Имя [, Имя2]` | только Elo/hElo/cElo/gElo/yElo |
| `/json Игрок 1 \| Игрок 2` | тот же отчёт файлом .json |
| `/refresh` | сбросить кэш HTML |
| `/health` | uptime, свободные слоты, режим |
| `/whoami` | ваш user id для белого списка |

Разделитель пары — `|`, `vs` или `против`. Покрытие понимается и по-русски
(`грунт`/`хард`/`трава`). Сообщение без команды, но с `vs` или `|`, тоже
трактуется как `/h2h`.

### Доступ

По умолчанию (`ALLOWED_USER_IDS` пуст) бот отвечает всем, кто его найдёт.
Отправьте боту `/whoami`, впишите свой id в `.env` и перезапустите сервис —
иначе чужие запросы будут греть ваш сервер рендерами Chromium.

### Почему бот устроен именно так

- **`asyncio.to_thread`.** Парсер синхронный, а `playwright.sync_api` падает
  с `Sync API inside asyncio loop`, если позвать его из корутины. Тяжёлая
  работа уходит в отдельный поток, где лупа нет.
- **Семафор `TP_MAX_CONCURRENCY=1`.** Каждый рендер — это отдельный Chromium
  на 300–500 МБ. На VPS с 1 ГБ второй параллельный запрос убьёт процесс по OOM.
  Пока слот занят, следующий пользователь видит «В очереди…».
- **`MemoryMax=1500M` и `KillMode=control-group`** в unit-файле: хромиум
  умеет оставлять после себя зомби-процессы, systemd валит всю группу.
- **Кэш HTML на 6 часов.** Elo обновляется раз в неделю, повторные запросы по
  той же паре не должны стучаться на сайт заново.
- **Статус-сообщение + `send_chat_action` в цикле.** Рендер идёт 30–60 с,
  а «печатает…» в Telegram гаснет через 5 с.

### Обновление кода

```bash
cd ~/tennis-bot && git pull
sudo bash deploy/install.sh          # идемпотентен
sudo systemctl restart tennis-bot
```

### Если что-то не работает

| Симптом | Причина / что делать |
|---|---|
| `Executable doesn't exist ... chromium` | не отработал `playwright install`; повторить с `PLAYWRIGHT_BROWSERS_PATH=/opt/tennis-bot/.playwright` от пользователя `tennisbot` |
| `Host system is missing dependencies` | ставить с флагом `--with-deps` от root |
| Бот молчит, в логах `Conflict: terminated by other getUpdates` | запущено два экземпляра — проверьте `systemctl status` и локальный запуск |
| Сервис перезапускается по OOM | `TP_MAX_CONCURRENCY=1`, поднять `MemoryMax` или добавить swap |
| «История матчей пуста» | вёрстка tennisratio поменялась — см. `_render()` и `_find_match_tables()` |

## Отчёт статьями на telegra.ph

`TP_TELEGRAPH=1` — и вместо простыни сообщений в чат уходят две короткие
выжимки со ссылками, которые в Telegram разворачиваются как Instant View.

Публикуются **две отдельные статьи**, в том же порядке, что и обычные
сообщения: статистика уходит сразу после парсинга, симуляция — следом, когда
посчитается. Ждать одного ради другого не нужно.

```
🎾 Filip Cristian Jianu vs Jan Kumstat
Elo: 11% / 89% (bo3, clay)
Свежее: Filip Cristian Jianu (Δ 59.1 п.)

📄 Полная статистика
```
```
🎲 Симуляция — 10000 прогонов, bo3
Filip Cristian Jianu 30% (кэф 3.36) · Jan Kumstat 70% (кэф 1.42)
⚠️ стата и Elo расходятся — смотрите разбор моделей
ТБ 2.5 сета: 45% (кэф 2.20)

📄 Полная симуляция
```

Моноширинные таблицы переносятся один в один: `<b>`, `<i>` и `<pre>` Telegraph
поддерживает.

**Страницы публичные.** Адрес не угадать, но и защиты никакой: у кого ссылка,
тот и читает. Для ставок это стоит держать в голове — поэтому по умолчанию
выключено.

Аккаунт создаётся сам при первой публикации, токен ложится в
`tennis_parser/.telegraph_token` с правами 600. Свой токен — через
`TP_TELEGRAPH_TOKEN`. Редактировать страницы может только владелец токена:
потеряете файл — старые страницы останутся, но править их будет нечем.

### Включение на сервере

Переменная читается **один раз при импорте**, так что выставить её на живом
боте недостаточно — нужен перезапуск. И выставлять её надо в окружении того
процесса, где крутится бот: `export` в вашей ssh-сессии до systemd-службы не
доходит. Это самая частая причина «а почему пришло сообщением».

```bash
systemctl edit tennis-bot        # имя вашей службы
```
```ini
[Service]
Environment=TP_TELEGRAPH=1
```
```bash
systemctl daemon-reload && systemctl restart tennis-bot
```

Принимаются только значения `1`, `true`, `yes`.

Если что-то не сходится — `check_telegraph.py` проходит всю цепочку и на
каждом шаге говорит, что делать:

```bash
python3 /opt/tennis_bot/check_telegraph.py            # только проверки
python3 /opt/tennis_bot/check_telegraph.py --publish  # ещё и тестовая статья
```

Откат независимый для каждой статьи: если telegra.ph не ответил на статистике,
она уйдёт сообщениями, а симуляция всё равно попробует опубликоваться.

## Роли в котировках

Блок «Баланс по роли в котировках» показывает, как игрок отрабатывает статус
фаворита и андердога. Рядом с каждой ролью выводится диапазон кэфа.

Пороги взяты с самого сайта (блок ODDS PERFORMANCE COMPARISON) и лежат в
`ODDS_RANGES` (`api.py`):

| Роль | Диапазон |
|---|---|
| Явный фаворит | свой кэф < 1.20 |
| Фаворит | свой кэф 1.20–1.50 |
| Небольшой фаворит | свой кэф > 1.50 |
| Небольшой андердог | кэф соперника > 1.50 |
| Андердог | кэф соперника 1.20–1.50 |
| Явный андердог | кэф соперника < 1.20 |

Важная деталь: фаворитские роли заданы **своим** кэфом, андердожьи — кэфом
**соперника**. Это разные вещи. «Андердог» здесь значит «соперник шёл по
1.20–1.50», а не «я шёл по 1.20–1.50»: своей цены в этих корзинах нет вообще,
и пересчитать их в свои кэфы нельзя, потому что маржа неизвестна.

Корзины исчерпывающие и не пересекаются — проверено на Тиафо: 4-0, 17-3, 8-4,
6-7, 2-4, 0-2 суммируются ровно в 37-20 из шапки.

## Проверка привязки кэфов

Кэфы приходят от Pinnacle с их порядком участников, наш порядок берётся из
ссылки на матч. Если стороны разъедутся, бот будет ставить на аутсайдера по цене
фаворита — и это не видно по одной ставке: при проигрыше пишется минус на размер
ставки, коэффициент в расчёте не участвует.

**Перед ставкой.** `check_odds_attribution()` считает маржу (у Pinnacle на теннис
обычно 2–4%; за пределами 0–12% цены, скорее всего, из разных рынков), ловит одну
и ту же цену, записанную дважды, и сравнивает рынок с нашим Elo. Расхождение
больше 35 п.п. попадает предупреждением прямо под список ставок — это не запрет,
а повод сверить с сайтом.

**Совпадающие фамилии.** Раньше при `p1_last in name1` через подстроку обе
ориентации могли подойти сразу (братья, частая фамилия), и молча брался первый
вариант. Теперь такие пары разводятся по имени, а неразрешимые пропускаются
с сообщением в лог.

**Задним числом.** `audit_odds.py` проверяет историю. Бот всегда ставит на
фаворита рынка, поэтому при верной привязке такие ставки должны заходить с
частотой, близкой к подразумеваемой ценой. Скрипт даёт калибровку по корзинам
кэфа, сравнивает гипотезы «привязка верна» и «привязка перевёрнута» по
правдоподобию и считает биномиальную вероятность.

```bash
python3 /opt/tennis_bot/audit_odds.py       # отчёт по bets_db.json
python3 /opt/tennis_bot/audit_odds.py --min-sample 40
```

Оба служебных скрипта (`audit_odds.py`, `fix_settlements.py`) ищут `bets_db.json`
и `bot_merged.py` **рядом с собой**, а не в текущем каталоге, поэтому запускать
их можно откуда угодно и по абсолютному пути. Другое расположение базы —
через `--db` или переменную `BETS_DB`.

Проверено на синтетике: 60 матчей с честной привязкой дают разницу
логправдоподобия +18 в пользу верной версии, те же 60 с перевёрнутой — −31 и
провал калибровки на 55 п.п. в нижних корзинах. На выборке меньше 30 матчей
скрипт честно говорит, что ничего не доказывает.

## Счёт хранится разобранным

Раньше в базу писалась сырая строка TennisExplorer — `2-1,66-7,6-3,6-3`,
с итогом по сетам первым токеном и склеенным тайбрейком. Разбирал её каждый
потребитель у себя: чат, CSV, панель. Достаточно было забыть одно место,
чтобы «6-7(6)» снова показалось как «66-7» — что и происходило.

Теперь приведение делается один раз, при записи результата. Разбор
идемпотентен, так что повторный проход по уже приведённой базе ничего
не портит.

## Перевёрнутый счёт

TennisExplorer перечисляет игроков в своём порядке — часто победителем
вперёд, а не так, как матч записан у нас. Бот это вычислял (`reversed_order`),
но **не применял**: счёт уходил в расчёт как есть. Матчи, где порядок
отличался, закрывались зеркально — победитель записывался проигравшим,
и все ставки по матчу считались наоборот.

Исправлено: при обратном порядке счёт переворачивается через `flip_score()`,
разбирая тайбрейки правильно, а не переставляя цифры вокруг дефиса.

Уже закрытые матчи надо перепроверить — скрипт заново скачивает результаты
и сверяет с базой:

```bash
./venv/bin/python3 recheck_results.py           # показать расхождения
./venv/bin/python3 recheck_results.py --apply   # исправить, с бэкапом
./venv/bin/python3 rebuild_history.py --apply   # пересобрать CSV
```

Пример вывода:

```
  Daniel Milavsky - Lloyd Harris
    было 2-1, на самом деле 1-2   (7-6(8), 3-6, 3-6)
      П2: loss -1000 -> win +490
```

Он же приводит счёт к читаемому виду у всех записей — даже там, где порядок
игроков верный:

```
2-1,4-6,6-4,7-63   ->  4-6, 6-4, 7-6(3)
2-1,6-3,65-7,6-3   ->  6-3, 6-7(5), 6-3
```

Сырая строка сохраняется в поле `score_raw` — на случай, если разбор
когда-нибудь окажется неверным и понадобится оригинал.

Форы скрипт не пересчитывает: линия там хранится внутри текста прогноза и
разбирается отдельной веткой, угадывать за расчётчик здесь неправильно.

## Пересборка истории ставок

Правки в разборе счёта действуют на новые строки; уже записанные в
`bets_history.csv` остаются как были. Переписать старые:

```bash
./venv/bin/python3 rebuild_history.py            # показать, что изменится
./venv/bin/python3 rebuild_history.py --apply    # переписать, с бэкапом
```

Убирает итоговый токен по сетам, который TennisExplorer ставит первым, и
склеенный разбор тайбрейка:

```
2-1,6-3,65-7,6-3   ->  6-3, 6-7, 6-3
2-1,4-6,6-4,7-63   ->  4-6, 6-4, 7-6
```

Скрипт берёт разбор из самого `bot_merged.py`, чтобы логика не разъехалась,
и записывает файл с BOM — Excel откроет без плясок с кодировкой. Строки
«В игре» не трогаются.

## Переменные окружения

| Переменная | Смысл |
|---|---|
| `TP_SKIP_COMPARISON=1` | не парсить блоки сравнения (быстрее примерно на треть) |
| `TP_SKIP_SIMULATION=1` | не считать симуляцию, только статистика |
| `TP_TELEGRAPH=1` | публиковать отчёт статьёй на telegra.ph вместо сообщений |
| `TP_TELEGRAPH_TOKEN` | готовый токен telegra.ph (иначе создаётся сам) |
| `TP_SHOW_MATCHES` | сколько последних матчей показывать на игрока (по умолчанию 10) |
| `TP_SIM_RUNS` | число прогонов (по умолчанию 10000) |
| `TP_SIM_ELO_WEIGHT` | вес Elo в рабочей модели, 0..1 (по умолчанию 0.7) |

## Встраивание в существующий бот

Если у вас уже есть бот (синхронный, на `requests` + потоках), полный запуск
`tennis_parser.bot` не нужен — берите `tennis_parser/integration.py`:

```python
from tennis_parser.integration import run_stats_parsing
import threading

threading.Thread(
    target=run_stats_parsing,
    args=(send_notification, chat_id, match_url),
    kwargs={"p1": p1, "p2": p2, "tournament": tournament, "reply_to": message_id},
    daemon=True,
).start()
```

`send_notification` — ваша функция отправки с сигнатурой
`(text, chat_id, reply_markup=None, reply_to=None)`. Если `reply_to` в ней нет,
адаптер это переживёт: поймает `TypeError` и позовёт без него.

Внутри `integration.py` свой `threading.Semaphore(1)`, поэтому несколько
нажатий кнопки подряд не поднимут несколько Chromium параллельно. Длинные
отчёты режутся по границам блоков, не разрывая `<pre>`.

  cli.py             CLI

deploy/
  install.sh         установка на Ubuntu
  tennis-bot.service systemd unit
